# 后端接入说明（P0 接口层）

> 对应决策：先抽接口层，部署目标 = 一台轻量服务器。
> 本文描述的是**当前已完成的部分**：契约层已就位，正式后端（P1）尚未开发。

## 一、现在是什么状态

前端已经把「出题」和「批改」从页面里彻底抽出来了。页面只认契约，不认具体实现。

```
页面 (P08Battle / P10WrongBook)
        │  只调这 3 个函数
        ▼
  provider/index.ts  ── 路由 + 降级 ──┬── local.ts   同步、零成本、零网络
                                      └── remote.ts  HTTP → 你的轻量服务器
```

- **默认跑 local**，行为和抽取之前完全一致：程序化生成、答案 100% 确定、零延迟。
- **配了 `VITE_API_BASE_URL` 才走 remote**，连不上会自动回落 local，孩子那边不会玩不了。

## 二、页面侧只依赖三个函数

| 函数 | 作用 | 返回 |
|---|---|---|
| `generateQuestions(req)` | 出本关题目 | 本地同步返回，远端返回 Promise |
| `generateVariants(seed, n)` | 举一反三变式 | 同上 |
| `gradeAnswer(q, input)` | 判分 | 答案唯一的题同步返回，开放题异步 |

`MaybeAsync<T>` 是刻意的：本地实现在渲染期就把题出好，**不闪 loading**；远端实现才给 loading 态。这个差别由 `isThenable()` 判定。

## 三、接口契约（后端要实现这三个）

```
POST /api/gen      请求 { subject, levelId, count, inject?, attr? }  响应 { questions[], source, degraded? }
POST /api/variants 请求 { seed: Question, count }                    响应 { questions[], source }
POST /api/grade    请求 { question: Question, input }                响应 { correct, by, feedback?, deferred? }
```

**`source` 字段很关键**，它驱动成本控制：

| source | 含义 | 成本 |
|---|---|---|
| `cache` | 命中题库 | 零 |
| `llm` | 模型新生成 | 有 |
| `local` | 本地生成（前端兜底） | 零 |

前端会累计这些调用（见 `providerStats()`），命中率低于 85% 就该查后端是不是没做缓存。

**`inject` 传的是 `QSpec` 而不是题面** —— 服务端拿到 `{ kind, a, b, op }` 就能无损重建原题，也能从同一份 spec 派生变式。这个设计前端已经用了，后端直接接。

## 四、判分：本地优先是成本闸门

```
gradeAnswer()
   ├─ 答案唯一（数学速算）→ gradeLocally()  本地精确比对，零成本，永远不走网络
   └─ 开放答案（看图说话/造句/手写）→ 远端模型批改
```

**不要动这条规则**。大模型会算错 7+8，本地判分器不会。接后端之后，本地判分器不是被替换，而是升级成"最便宜的那道判分关"——正式后端里也应该先跑它（见 `tools/mock-api.ts` 的 `/api/grade` 实现）。

`gradeLocally` 已做输入归一化：全角数字转半角、去空格、去前导 0、长度上限 4 位、非数字判错。

## 五、降级与可观测

- 远端失败/超时 → 自动回落本地，`degraded: true`，页面顶部显示「连不上服务器，已用本地题目」。
- 所有调用计数在 `providerStats()`：远端成功次数、本地次数、降级次数、最后一次错误。开发期控制台可查 `__provider.stats()`。
- 开放题在断网时返回 `deferred: true`，页面把题放回队尾重做，**不算孩子错**。

## 七、部署到轻量服务器的两个注意点

**1. CORS —— 已经踩过一次**

开发时页面在 5180、服务在 8787，属跨源，浏览器直接拦。本次实测就是卡在这里（`Failed to fetch` → 走了降级）。

- 临时方案：后端加 `Access-Control-Allow-Origin` 响应头 + 处理 `OPTIONS` 预检（参见 `tools/mock-api.ts`）。
- **推荐方案：nginx 把 `/api` 反代到同域**，前端 `VITE_API_BASE_URL` 留空或填同域地址，彻底避开 CORS，也少一次预检往返。

**2. 密钥只在服务端**

`VITE_` 前缀的变量会被打进前端 bundle，任何人 F12 都能看到。**后端地址可以放 `VITE_`，模型密钥绝对不行** —— 密钥只写进服务器环境变量。

# v1.2 前端接入实录（2026-09-16）

**前端数据同步已落地，`/api/sync` 不再是空接口。**

## 架构

```
业务写入（打卡 / 投喂 / 闯关 / 错题 / 跨日结算）
      │  埋点收口在 4 个函数里，业务代码完全不感知网络
      ▼
  store/sync.ts   本地 op 队列（localStorage: pet-checkin-sync-v1）
      │  静默期 5s / 启动时 / 回前台时 批量推送
      ▼
  POST /api/sync  { childId, ops[] }  ── op_id 幂等入库
```

与 provider 层刻意分开：**provider 决定「题从哪儿来」，sync 决定「成绩去哪儿」**。

## 埋点位置（收口，不是散点）

| op | 埋点位置 | 说明 |
|---|---|---|
| `ledger` | `useStore.recordLedger()` | 8 处流水调用统一走它；将来加字段只改一处，不会漏 |
| `snapshot` | `useStore.advanceDays()` | 每次跨日结算逐日入队（补结算多天就记多条） |
| `level_record` | `useStore.finishBattle()` | 新增 `playCount` 累计游玩次数 |
| `wrong_item` | `finishBattle()` / `reviewWrong()` | 错题入池与复习结果都同步 |
| `attempt` | `P08Battle.recordAttempt()` | **逐题**流水：对错 / 答案 / 耗时 / 是否用过提示；「跳过」也记（`input=null, correct=false`），因为「不会做」本身有信息量 |

> 注意：`attempts` 是本次新增的埋点。之前 `P08Battle` 只把错题传给 `finishBattle`，
> 逐题明细根本没落盘 —— 服务端 `attempts` 表此前注定是空的。

## 三条设计铁律

1. **绝不阻塞孩子玩**：断网 / 后端挂 / 令牌错 → 只是「先攒着」。队列在 localStorage，
   下次启动、回前台继续推。孩子的闯关一分一秒都不会因此卡住。
2. **幂等靠 opId**：`attempts` / `ledgers` 有 `op_id` 唯一约束，网络超时后重推是安全的。
   出队按 opId 过滤而不是清空数组 —— 推送期间新入队的 op 不会被误删。
3. **失败分级**，不是一刀切重试：
   | 情况 | 处理 | 理由 |
   |---|---|---|
   | 5xx / 网络不可达 / 超时 | 保留，下次再推 | 服务端问题，重推安全 |
   | **403** | **暂停同步** | 令牌不对，再推一万次也是 403，只会刷爆请求；换令牌后自愈 |
   | **4xx** | **丢弃这批并记账** | 数据本身服务端不认，留着会**永久堵住队头**，后面全推不上去 |

## 安全取舍（已决策）

`VITE_SYNC_TOKEN` 会进前端 bundle，等同「半公开」的**写入**凭证。因此：

- 前端只用 `/api/sync`（只写）；能读全量数据的 `/api/report` **不开放给前端**，留在服务器侧查。
- 生产环境必须：① nginx 同域反代（顺带避开 CORS）、② 给 `/api/sync` 限流。
- 最坏情况（令牌泄露）= 有人往自己那个 childId 里灌脏数据，读不到别人的任何东西。

## 验证

`npm run smoke` 新增**第 23 组 / 17 条断言**（stub fetch，不依赖真实后端）：
未启用时零开销 → 启用后入队 → 推送出队 → 请求头与 childId → opId 无重复 →
5xx 保留 → 403 暂停且不再发请求 → 换令牌自愈 → 4xx 丢弃记账 → dropQueue。

`npm run verify` 全绿：类型 0 错、23 组冒烟全过、构建 252.72 kB（gzip 81.76 kB）。

# v1.3 实体同步补齐 + 放宽两处约束（2026-09-16）

**`children` / `pets` / `task_templates` / `daily_tasks` / `prizes` / `redeems` 六张表接上了。**
同步上去的不再只是「成绩流」，还包括孩子的档案与任务配置。

## 一、数据库：两处放宽（**先执行，再发前端**）

迁移文件 `db/20260916120000_relax_pets_fk_redeem_status.sql`（幂等，可重复执行）：

| # | 改动 | 为什么 |
|---|---|---|
| 1 | 去掉 `pets.child_id → children(id)` 外键，**保留主键** | 同步走本地 op 队列：可能重试、可能被批量上限截断、可能丢弃坏数据，**保证不了严格顺序**；而外键要求 pets 必须晚于 children。一条约束会拖垮整批 op |
| 2 | `redeems.status` 的 CHECK 增加 `delivered` | 前端有「已兑现」状态（家长把奖品实际交到孩子手上），原 CHECK 只到 `approved`，会把这个信息挤掉 |

关联关系依然在：靠 `pets.child_id` 的值本身、靠查询时 JOIN。
**代价**：可能出现 `child_id` 指向不存在孩子的孤儿行 —— 由应用层保证先写 `children`。

> ⚠️ 迁移必须先于前端发布，否则 `delivered` / `timeout` 会被 CHECK 拒绝、对应 op 被记为失败丢弃。

## 二、服务端：op 分发抽到 `server/ops.ts`

原先 op→SQL 的分发和 HTTP 混在 `server.ts` 里。现在拆出一个**零 node 依赖**的模块，
好处是它能被单独类型检查（`tsconfig` 只覆盖 `src`），也能被冒烟脚本用假 `pg` 直接跑断言。

新增 6 种 op，**幂等手段和流水不同**：

| 类别 | op | 幂等手段 | 需要 opId | 需要顺序 |
|---|---|---|---|---|
| 只增不改的流水 | `attempt` `ledger` | `op_id` 唯一约束 | ✅ | — |
| 一行一实体的快照 | 其余 9 种 | 业务主键 upsert | ❌ | — |

> 实体 op「不需要 opId、也不需要顺序」，正是外键必须去掉的原因 —— 同一件事的两面。

字段在拼 SQL 之前先做规范化，把**必然会被数据库拒绝**的数据挡在前面：
`food_value` 夹到 1~3（对上 CHECK）、`day` 校验 `YYYY-MM-DD`、时间统一转 ISO、
兑换状态必须在允许集合内。违规则抛 `PgError(transient=false)`，错误信息里直接看得出是哪条 op 的哪个字段。

## 三、服务端：失败改成逐条上报（修一个会静默停摆的坑）

上一版是「一条 op 抛错 → 整批 500 → 客户端原样保留整批、下次再推」。
配上本地队列就是**死循环**：那条坏 op 永远卡在队头，它后面的数据永远推不上去，
而客户端只能看到「这批 500」，定位不到是哪一条。

| 情况 | 服务端 | 客户端 |
|---|---|---|
| 单条数据问题（类型 / 约束 / 缺字段） | 记进 `failedIds` + `errors`，继续处理后面的，整批 **200** | 丢弃这几条并记账（`rejected`），其余照常入库 |
| 基础设施故障（网关 5xx / 429 / 连不上） | 整批 **500** | 全部保留，下次重推（op 幂等，不会写重） |
| 整批一条都没成、且不止一条 | 当成基础设施问题，整批 500 | 同上，宁可重推也不丢数据 |

另外 `pgOk` 只在**基础设施故障**时才置 false —— SQL 写错不该让 `/health` 变红。

## 四、客户端：六类埋点

| op | 埋点位置 | 说明 |
|---|---|---|
| `child` | `setChildProfile()` / `bootstrap()` / `setName()` | **本地此前没有任何孩子档案的数据源**，v1.3 才补出 `AppState.child` |
| `pet` | `adopt` / `setName` / `renamePet` / `feed` / `finishBattle` / 跨日结算 | 饱食度、阶段、三科属性都会变，跟着更新 |
| `task_template` | `addTemplate` / `updateTemplate` / `removeTemplate` | 删除走 `active:false`（软删）|
| `daily_task` | `ensureTasks` / `submitTask` / `approveTask` / `rejectTask` | 状态流转每次都发 |
| `prize` | `addPrize` / `updatePrize` / `removePrize` | 删除同样软删 |
| `redeem` | `redeem` / `approveRedeem` / `rejectRedeem` / `deliverRedeem` / 超时自动退回 | 「超时」显式标成 `timeout`，不和家长驳回混在一起 |

**删除为什么是软删**：`daily_tasks.template_id` 要能 JOIN 回模板、`redeems.prize_id` 要能 JOIN 回奖品，
物理删行会让历史记录指空。

**启动时会补发一遍实体快照**（`seedEntities()`，5 类对象各一条 upsert）：
全是 upsert，重复推不会写重；换来的是「同步是后来才打开的」也能把已有档案补齐 ——
否则早先建好的模板、奖品永远进不了库。

> 埋坑记录：`s.templates.forEach(recordTemplate)` 会把**数组下标**当成第二个参数
> （也就是 `deleted`）传进去，把第二条之后的模板统统标成「已删除」。
> 必须写成 `forEach((t) => recordTemplate(t))`。
