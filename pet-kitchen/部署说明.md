## 二、数据库部署（CloudBase PostgreSQL）

### 2.1 确认环境与 PG 已开通

CloudBase 控制台 → 环境列表 → 进入目标环境 → 「数据库」确认已切换为 **PostgreSQL 模式**。

记录三件事：**环境 ID**、**地域**、**PG 实例 ID**。

### 2.2 执行建表迁移

建表脚本：`db/20260915104000_create_pet_checkin_tables.sql`（14 张表 + 索引）。

**增量迁移**（已有环境才需要，按版本号顺序执行，可重复跑）：

| 版本 | 迁移名 | 文件 | 做了什么 | 状态 |
|---|---|---|---|---|
| `20260916120000` | `relax_pets_fk_redeem_status` | `db/20260916120000_relax_pets_fk_redeem_status.sql` | 去掉 `pets.child_id` 外键（同步 op 队列保证不了先后顺序）；`redeems.status` 增加 `delivered` | ✅ **2026-09-16 已应用** |

> ✅ 该迁移已于 2026-09-16 通过 CloudBase PostgreSQL 迁移通道应用（远端历史现有 2 条）。
> 校验结果：`pets_child_id_fkey` 已消失、`pets_pkey` 保留、`redeems_status_check` 含 `delivered`。
> 下面 A / B 两种方式保留，供在**全新环境**重建时使用。

**方式 A：CloudBase 控制台（推荐，最省事）**

控制台 → 数据库 → SQL 编辑器 → 粘贴脚本全文 → 执行。

**方式 B：HTTP API（脚本化 / CI 用）**

PG 数据面走 PostgREST 网关，用 **API Key** 鉴权：

```bash
curl -X POST "https://<ENV_ID>.api.tcloudbasegateway.com/v1/rdb/exec-pgsql" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <TCB_API_KEY>" \
  -d '{"sql":"SELECT count(*) FROM information_schema.tables WHERE table_schema=$1","parameters":["public"],"role":"cloudbase_postgres"}'
```

> ⚠️ SQL 必须用 `$1 $2` **参数化**，不要把值拼进字符串里。
> ⚠️ 迁移请带**版本号**（脚本文件名前缀即版本），便于回滚和排查。

### 2.3 表结构一览

| 分组 | 表 | 说明 |
|---|---|---|
| 用户 | `children` `pets` | 孩子与宠物（1:1） |
| 打卡 | `task_templates` `daily_tasks` | 任务模板与每日实例 |
| 经济 | `ledgers` | 食物/积分**事件流**（`kind` 区分），`op_id` 唯一约束 → 幂等 |
| 闯关 | `level_records` | 每关最佳星级、是否通关（业务键 upsert） |
| **题库** | `questions` | `spec` 用 jsonb 存；`verified=false` **不下发**（大模型安全闸门） |
| **流水** | `attempts` | 每题一行、只增不改，`op_id` 幂等。自适应出题与模型批改的依据 |
| 错题 | `wrong_items` | `UNIQUE(child_id, question_text)` |
| 报告 | `daily_snapshots` | 只增不改，`PRIMARY KEY(child_id, day)` |
| 奖品 | `prizes` `redeems` | `redeems.status` 承载审批状态机 |
| 运维 | `llm_calls` `sync_state` | 模型调用审计 / 同步游标 |

**两个踩坑记录：**

1. **`full` 是 PostgreSQL 保留字**，不能直接做列名 —— 快照表里用的是 `is_full`（API 层映射回 `full`）。
2. CloudBase 的迁移是**整体事务**，中途报错会全量回滚，`public` schema 不会留残留，改完直接用新版本号重发即可。

### 2.4 创建 API Key

CloudBase 控制台 → **认证管理 / API 密钥** → 新建，权限给到 PG 读写，名称例如 `pet-checkin-backend`。

> ⚠️ **Key 只在创建时可见**。列表里显示的是打码值（形如 `eyJhbG******CBcvSw`），
> 如果当时没保存，删掉重建一个 —— 别去猜。

## 三、后端部署（轻量服务器）

### 3.1 本地构建

后端是**零依赖**的（只用 Node 原生 `http` / `fetch`），不需要 `npm install`：

```bash
npx esbuild server/server.ts --bundle --platform=node --format=cjs \
  --outfile=server/server.build.cjs --log-level=error

ls -l server/server.build.cjs      # 约 23 KB
```

> 后端直接 `import` 前端的 `src/engine/*`，所以**出题与判分和前端本地模式行为完全一致**。
> 这也是判定「远端是否真的在工作」的基准：同一 `levelId` 出的题应该同构。

### 3.2 上传到服务器

**方式 A：scp（直连 22 端口时最简单）**

```bash
ssh root@124.222.148.45 "mkdir -p /opt/pet-checkin/env"
scp server/server.build.cjs root@124.222.148.45:/opt/pet-checkin/server.cjs
```

**方式 B：经对象存储中转**（安全性组未放行 22、或走云控制台时用）

上传到 CloudBase 静态存储（如 `deploy/server.build.cjs`），再在服务器上：

```bash
cd /opt/pet-checkin
curl -sL -o server.cjs 'https://<存储下载域名>/deploy/server.build.cjs'
ls -l server.cjs && head -c 80 server.cjs      # 校验大小与文件头
```

> 下载后**务必核对字节数与本地一致**，避免拿到半截或被网关改写的文件。

### 3.3 环境变量文件

```bash
cd /opt/pet-checkin
mkdir -p env
cat > env/pet-checkin.env <<'EOF'
PORT=8787
TCB_ENV_ID=<你的 CloudBase 环境 ID>
TCB_API_KEY=<CloudBase 控制台创建的 API Key>
SYNC_TOKEN=<自建访问令牌>
EOF
chmod 600 env/pet-checkin.env      # 只有 root 可读
```

生成 `SYNC_TOKEN`：

```bash
node -e "console.log('pcsync-'+require('crypto').randomBytes(12).toString('hex'))"
```

> `SYNC_TOKEN` 是 `/api/sync` 与 `/api/report` 的访问令牌，**必填**。
> 留空 = 这两个接口对公网匿名开放，任何人都能往你库里写数据。

### 3.4 启动容器

```bash
docker rm -f pet-checkin 2>/dev/null

docker run -d \
  --name pet-checkin \
  --restart always \
  --env-file /opt/pet-checkin/env/pet-checkin.env \
  -p 8787:8787 \
  -v /opt/pet-checkin/server.cjs:/app/server.cjs:ro \
  node:22-alpine \
  node /app/server.cjs
```

> `--restart always` 让容器随 Docker 守护进程开机自启，不用额外配 systemd。
> `-v ...:ro` 把构建产物挂进去，**更新版本时只需替换宿主机文件 + 重启容器**，不必重建镜像。

### 3.5 放行防火墙

轻量应用服务器控制台 → 防火墙 → 添加规则：

| 协议 | 端口 | 来源 |
|---|---|---|
| TCP | 8787 | 0.0.0.0/0 |

> **生产建议**：不要对公网裸放 8787。更稳的做法是 nginx 反代到同域 `/api`（见 §4.2），
> 然后用防火墙把 8787 限制为仅内网 / 仅 nginx 所在主机可访问。

### 3.6 验证

```bash
# 服务器本机
curl -s http://127.0.0.1:8787/health

# 公网
curl -s http://124.222.148.45:8787/health
curl -s -X POST http://124.222.148.45:8787/api/gen \
  -H "Content-Type: application/json" \
  -d '{"levelId":"m1","count":1,"attr":3}'
```

期望结果：

```jsonc
// /health —— pgOk 必须为 true，才有数据库能力
{"ok":true,"pgOk":true,"pgLastError":"","env":"base-xxxx","uptime":12.3}

// /api/gen —— 正常返回题目
{"questions":[{"text":"8 + 9 = ?","answer":17,"hint":"...","spec":{"kind":"cou10","a":8,"b":9,"op":"+"}}],"source":"local"}
```

其余接口：

```bash
# 判分（答案唯一的题走本地判分器，by 应为 "local"）
curl -s -X POST http://124.222.148.45:8787/api/grade \
  -H "Content-Type: application/json" \
  -d '{"question":{"text":"8+9=?","answer":17,"answerType":"numeric"},"input":"17"}'

# 同步入库（需令牌）
curl -s -X POST http://124.222.148.45:8787/api/sync \
  -H "Content-Type: application/json" \
  -H "x-sync-token: $SYNC_TOKEN" \
  -d '{"childId":"c1","ops":[{"opId":"op-001","kind":"snapshot","data":{"day":"2026-09-15","satiety":80,"streak":3}}]}'

# 成长报告
curl -s "http://124.222.148.45:8787/api/report?childId=c1&days=30" \
```

- `/health` 的 `pgOk` 为 `true`
- `/api/sync` 返回 `{"applied":1,"total":1,"serverVersion":1}`
- 重复发同一条 `opId`，`applied` 仍为 1 但库里不新增行（**幂等生效**）

## 四、前端部署

### 4.1 本地接远端

复制 `.env.example` 为 `.env`：

```bash
VITE_API_BASE_URL=http://124.222.148.45:8787
```

```bash
npm run dev          # 开发
npm run build        # 生产 → dist/
```

不配这个变量 = 纯本地模式（零网络），行为和接后端前完全一致。

**降级自检**：把后端停掉再刷新页面，应出现「连不上服务器，已用本地题目」提示条，且仍可正常答题。

### 4.2 生产托管（推荐 nginx 同域反代）

把 `dist/` 交给 nginx，并把 `/api` 反代到后端 —— **这样前端与接口同源，彻底避开 CORS，也少一次 OPTIONS 预检往返**：

```nginx
server {
    listen 80;
    server_name your-domain.com;
    root /var/www/pet-kitchen;
    index index.html;

    # SPA 前端路由
    location / {
        try_files $uri $uri/ /index.html;
    }

    # 接口反代到本地后端
    location /api/ {
        proxy_pass http://127.0.0.1:8787;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location = /health {
        proxy_pass http://127.0.0.1:8787/health;
    }
}
```

配好之后前端 `.env` 里 `VITE_API_BASE_URL=` **留空**（同域直接用相对路径），或者填你的域名。

> 若暂时不做反代、前后端跨域：后端已带 `Access-Control-Allow-Origin` 与 `OPTIONS` 预检处理，
> 但公网直连端口的方式不适合长期生产使用。

## 六、排错速查表

| 现象 | 原因 | 处理 |
|---|---|---|
| 前端显示「连不上服务器，已用本地题目」 | 后端不可达 / 跨域被拦 | 先 `curl` 公网 `/health`；跨域则加 CORS 头或改 nginx 同域反代 |
| 浏览器控制台 `Failed to fetch` | 跨源被拦（页面 5180、接口 8787） | 同上；生产务必同域 |
| `/health` 返回 `pgOk:false` | `TCB_API_KEY` 无效/未填，**或改了 env 文件但只执行了 `docker restart`（env 是容器创建时固化的）** | 确认 `env/pet-checkin.env` 内容后**重建容器**（见上文「重启」一节），不是 restart |
| `INVALID_CREDENTIALS`（PG 401） | Key 打码值被误用 / Key 过期 | 用创建时**保存的完整值**；没有就重建 |
| `/api/sync` 返回 403 | `x-sync-token` 不匹配 | 核对服务器 `SYNC_TOKEN` 与请求头 |
| 迁移报 `syntax error at or near "full"` | `full` 是 PG 保留字 | 改用 `is_full`（脚本已修正） |
| `docker run` 报端口占用 | 旧容器未清理 | `docker rm -f pet-checkin` 后重跑 |
| 容器起来又退出 | 代码或环境变量有问题 | `docker logs pet-checkin --tail 50` 看堆栈 |
| 云控制台命令被安全策略拦截（`systemctl`、写 `/etc`、`nohup &`） | 云厂商命令执行的策略限制 | 改用 **SSH / OrcaTerm 登录**后手敲命令；或走 Docker 方案（本文即如此） |

## 九、接口清单（供联调参考）

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| GET | `/health` | — | 存活检查，含 `pgOk` / `pgLastError` / `uptime` |
| POST | `/api/gen` | — | 出题 `{subject,levelId,count,inject?,attr?}` → `{questions[],source}` |
| POST | `/api/variants` | — | 举一反三 `{seed,count}` → `{questions[],source}` |
| POST | `/api/grade` | — | 判分 `{question,input}` → `{correct,by,feedback?}` |
| POST | `/api/sync` | `x-sync-token` | 入库 `{childId,ops[]}` → `{applied,failed,failedIds,errors,total,serverVersion}` |
| GET | `/api/report` | `x-sync-token` | 报告 `?childId=&days=` → `{snapshots[],weakSkills[]}` |

`/api/sync` 支持的 op 类型（共 11 种），幂等手段分两类：

| 类别 | op | 幂等手段 |
|---|---|---|
| 只增不改的流水 | `attempt` · `ledger` | `op_id` 唯一约束去重 |
| 一行一实体的快照 | `snapshot` · `level_record` · `wrong_item` · `child` · `pet` · `task_template` · `daily_task` · `prize` · `redeem` | 按业务主键 upsert，**不需要到达顺序** |

失败语义是**逐条**上报的：单条 op 因数据问题（类型 / 约束 / 缺字段）失败时，服务端把它记进
`failedIds` + `errors`，继续处理后面的，整批仍返回 200 —— 客户端据此只丢弃这几条、保留其余。
只有基础设施故障（网关 5xx / 429 / 连不上）才整批 500，让客户端原样重推，不丢数据。
